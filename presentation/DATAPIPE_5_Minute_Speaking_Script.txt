Hello. Today I am presenting DATAPIPE, a Python command-line data pipeline. It reads records from files and HTTP JSON sources, checks every record, applies configured steps, and writes results in useful formats. I built this project to handle real pipeline concerns, including concurrent sources, invalid data, safe output commits, and restart after interruption. I will show the design, run flow, plugin, and measured results.

SLIDE 2: From sources to committed output
Timing: 0:30-1:08
Screen: Trace the diagram from left to right
The architecture separates sources, pipeline stages, and sinks. HTTP, CSV, JSONL, and installed plugins provide records. Async source tasks feed a bounded queue. That queue applies backpressure when the consumer is busy, so producers cannot grow memory without limit. Pydantic checks records at the boundary. Valid records go through configured transformations. Invalid records go to a dead-letter file with their source and reason. Finally, the sink writes JSONL or Parquet partitions. A journal ties output batches to source checkpoints.

SLIDE 5: One run from raw input to committed output

The sample reads four rows from CSV and three lines from JSONL. Four records pass validation. Three go to dead-letter output: two fail record validation, and one line contains malformed JSON. Mapping renames the amount field. Deduplication removes one repeated identifier. The run writes three valid records into date partitions, and the report summarizes the counts. Dead letters keep the original input and a useful reason, so problems do not disappear silently.

SLIDE 7: Measured results and validation
Timing: 3:35-4:30
Screen: Point to the chart, then the test and memory results
I measured the exact Python aggregation path against the PyArrow path with the same 50,000-row dataset. Fifteen interleaved runs gave median times of 0.417812 and 0.135114 seconds. That is a measured 3.09 times faster, and the normalized outputs matched exactly. This result applies to this in-memory workload and the 50,000-row Arrow batch. Other batch sizes and the full disk-backed pipeline were slower than 3 times. The run passed 147 tests with two POSIX signal tests skipped on Windows; branch-only coverage was 86.23 percent and combined coverage was 91.41 percent. Separate streaming deduplication tests processed two and five million records with similar RSS growth, while using more disk for the larger input.
